## 一、大模型是什么：从「统计」到「涌现」

### 1.1 一句话定义

**大语言模型（LLM, Large Language Model）** 是一个在海量文本上训练出来的**超大规模神经网络**，它的核心任务只有一个：**根据前面的文字，预测下一个最可能的词。**

没错，就这么简单。你和 ChatGPT 聊了半天，它本质上只是在做「完形填空」——不断预测下一个 token。但当模型参数量大到一定程度（几十亿到几千亿），这种简单的预测能力会「涌现」出令人惊叹的效果：推理、写代码、翻译、甚至假装自己有感情。

### 1.2 「大」在哪里？

| 维度 | 说明 | 举例 |
|------|------|------|
| **参数量** | 模型内部的「旋钮」数量 | GPT-3: 1750亿参数，GPT-4: 据传 1.8万亿 |
| **训练数据** | 学习的文本量 | 数万亿 token（约几十 TB 文本） |
| **计算资源** | 训练所需算力 | GPT-4 训练成本估计超过 1 亿美元 |
| **上下文窗口** | 单次能处理的最大长度 | GPT-4 Turbo: 128K tokens |

### 1.3 面试常问：「大模型和传统 NLP 模型有什么区别？」

```
传统 NLP（如 BERT、LSTM）：
  - 为特定任务训练（情感分析、命名实体识别...）
  - 换任务 = 换模型 = 重新训练
  - 参数量：千万~亿级

大语言模型（如 GPT、Claude、DeepSeek）：
  - 通用能力：什么都能干
  - 换任务 = 换 Prompt（不用改模型）
  - 参数量：百亿~万亿级
  - 有「涌现能力」：小模型做不到的事，大模型突然就会了
```

**面试参考答案**：传统 NLP 模型是「专才」，每个模型只擅长一个任务；大语言模型是「通才」，通过海量数据训练获得了通用的语言理解和生成能力，只需通过 Prompt 即可切换任务，无需针对每个任务单独训练。这种通用性的关键在于参数规模突破临界点后产生的「涌现能力」。

## 二、Transformer 架构：大模型的「骨架」

### 2.1 为什么是 Transformer？

几乎所有现代大模型（GPT、Claude、Llama、DeepSeek）都基于 **Transformer** 架构，2017 年 Google 在论文《Attention Is All You Need》中提出。它的核心创新是**自注意力机制（Self-Attention）**，解决了之前 RNN/LSTM 的两个致命问题：

| 旧方案 | 问题 | Transformer 怎么解决 |
|--------|------|---------------------|
| RNN/LSTM | **不能并行**，必须一个词一个词处理 | 所有词可以同时处理（并行计算） |
| RNN/LSTM | **长距离遗忘**，超过 200 词就忘前面的了 | 注意力机制直接连接任意距离的词 |

### 2.2 自注意力机制（Self-Attention）：核心中的核心

面试**必考**概念，但你不需要推导数学公式，只需要理解直觉：

**一句话解释**：在处理每个词的时候，模型会「回头看」整个句子中的每个词，然后决定**哪些词对当前这个词最重要**，给予更高的「注意力权重」。

用一个例子来理解：

```
句子：「小明把苹果给了小红，她很开心」

处理「她」这个词时，Self-Attention 会：
  - 看「小明」→ 权重 0.1（不太相关）
  - 看「把」  → 权重 0.05（无关）
  - 看「苹果」→ 权重 0.15（有点关系）
  - 看「给了」→ 权重 0.1（有点关系）
  - 看「小红」→ 权重 0.6（高度相关！「她」指的就是小红）

所以模型能理解「她 = 小红」，这叫「指代消解」
```

### 2.3 Q、K、V 三个矩阵

自注意力的实现靠三个矩阵：**Query（查询）、Key（键）、Value（值）**。

面试不需要手推公式，但需要能解释**直觉**：

```
想象你在一个图书馆：

Query（你想找什么）：  你脑中的搜索关键词
Key（书的标签）：      每本书封面上的关键词
Value（书的内容）：    书的实际内容

搜索过程：
  1. 你拿着 Query 去比对每本书的 Key
  2. 匹配度高的书，你读得更仔细（更高的注意力权重）
  3. 最终你从这些书中综合信息，形成你的理解

数学上：
  Attention(Q, K, V) = softmax(QK^T / √d) × V
```

**面试参考答案**：Self-Attention 通过 Q、K、V 三个矩阵实现。每个词会生成一个 Query 向量，去和句子中所有词的 Key 向量计算相似度（点积），相似度越高代表越相关。用 softmax 将相似度归一化为权重后，对所有词的 Value 向量做加权求和，就得到了考虑了上下文关系的新表示。这使得模型能够捕捉长距离依赖关系。

### 2.4 多头注意力（Multi-Head Attention）

一个注意力「头」只能关注一种关系。但语言很复杂——语法关系、语义关系、指代关系可能同时存在。所以 Transformer 同时运行**多个独立的注意力头**，每个头学习不同类型的关系：

```
Head 1 可能学到：语法关系（主语→谓语→宾语）
Head 2 可能学到：指代关系（代词→被指代的名词）
Head 3 可能学到：语义相似（同义词、近义词）
... Head 8 / 12 / 32 ...

最终把所有头的结果拼接起来，得到更丰富的语义表示
```

### 2.5 GPT 的 Decoder-Only 架构

面试常问：「Transformer 有 Encoder 和 Decoder，GPT 用的哪个？」

```
原始 Transformer：
  Encoder（编码器）：理解输入 → 双向注意力（能看到前后文）
  Decoder（解码器）：生成输出 → 单向注意力（只能看前面的）

GPT 系列（GPT-3/4, Claude, DeepSeek）：
  只用 Decoder（ Decoder-Only ）
  原因：生成任务天然就是「从左到右」，不需要看后面的词

BERT：
  只用 Encoder（ Encoder-Only ）
  适合：理解任务（分类、问答），不适合生成
```

**面试参考答案**：GPT 系列采用 Decoder-Only 架构，使用因果注意力掩码（Causal Attention Mask），确保每个位置只能关注它前面的内容。这种单向注意力天然适合文本生成任务——模型从左到右逐个预测下一个 token。而 BERT 用 Encoder-Only（双向注意力），适合文本理解任务但不适合生成。

## 三、Token 与分词：大模型的「语言单位」

### 3.1 什么是 Token？

大模型**不直接处理文字**，而是处理 **Token**。Token 是模型的最小输入单位，由**分词器（Tokenizer）**将原始文本切分而成。

```
英文："Artificial Intelligence" → ["Art", "ific", "ial", "Int", "elligence"]（可能 5 个 token）
中文："人工智能" → ["人工", "智能"]（可能 2 个 token）
代码："def hello():" → ["def", " hello", "():"]（可能 3 个 token）
```

### 3.2 分词算法：BPE（Byte-Pair Encoding）

主流分词算法是 **BPE（字节对编码）**，核心思想：

```
步骤 1：把所有文本拆成单个字节/字符
步骤 2：统计相邻字符对出现的频率
步骤 3：把最高频的字符对合并成一个新 token
步骤 4：重复步骤 2-3，直到达到目标词表大小

举个例子：
初始：l o w e r s t a n d
第1轮：lo 出现 3 次 → 合并为 "lo"
第2轮：lo w 出现 2 次 → 合并为 "low"
...持续合并，直到覆盖所有常见模式
```

### 3.3 Token 的成本意义

| 概念 | 说明 |
|------|------|
| **计费单位** | API 按 token 数计费，不是按字数 |
| **中英文差异** | 1 个中文字 ≈ 1-2 个 token，1 个英文单词 ≈ 1-1.3 个 token |
| **上下文占用** | 每轮对话的 token 数 = 输入 token + 输出 token |
| **成本估算** | GPT-4o 输入 $2.5/百万 token，输出 $10/百万 token |

**一个直觉**：4000 个 token ≈ 3000 个中文字 ≈ 一篇短文章。GPT-4 的 128K 上下文窗口 ≈ 能一次性读完一本小说。

### 3.4 面试常问：「Token 和 Word 有什么区别？」

**参考答案**：Token 不等于 Word。分词器使用 BPE 算法将文本切分为子词（subword）级别的 token。常见词可能是一个 token（如 "the"），罕见词会被拆成多个 token（如 "tokenization" 可能被拆成 "token" + "ization"）。中文中，常见词组是一个 token，生僻字可能被拆成多个。这样设计的好处是：词表大小可控（通常 3 万~10 万），同时能处理任何新词（通过组合子词）。

## 四、上下文窗口与位置编码

### 4.1 上下文窗口（Context Window）

上下文窗口是模型**单次对话能处理的最大 token 数**，包括输入和输出。

| 模型 | 上下文窗口 | 大约相当于 |
|------|-----------|-----------|
| GPT-3.5 | 4K tokens | ~3000 中文字 |
| GPT-4 | 8K tokens | ~6000 中文字 |
| GPT-4 Turbo | 128K tokens | ~96000 中文字（一本中篇小说） |
| Claude 3.5 | 200K tokens | ~15万中文字 |
| DeepSeek-V3 | 128K tokens | 同 GPT-4 Turbo |
| Gemini 1.5 Pro | 1M tokens | ~75万中文字（一部《红楼梦》） |

**超过上下文窗口会怎样？** 模型会「截断」——直接丢弃最早的内容。这就是为什么长对话到后面模型会「忘记」前面说过的话。

### 4.2 位置编码（Positional Encoding）

Self-Attention 本身是**无序的**——它同时看所有词，但不知道词的顺序。"狗咬人"和"人咬狗"在没有位置信息时是一样的。

**位置编码**给每个 token 加上一个「位置标签」，告诉模型这个词在句子中的位置：

```
Token：  [狗]  [咬]  [人]
位置：   [1]  [2]   [3]

加上位置编码后：
[狗] + pos_1 → 模型知道这是第 1 个词
[咬] + pos_2 → 模型知道这是第 2 个词
[人] + pos_3 → 模型知道这是第 3 个词
```

主流方案：**RoPE（旋转位置编码）**，LLaMA、GPT-4 等都用它。核心思想是通过旋转角度来编码位置，天然支持相对位置关系。

### 4.3 面试常问：「为什么大模型会'遗忘'早期对话？」

**参考答案**：大模型的上下文窗口是固定的，当对话长度超过窗口限制时，最早的内容会被截断丢弃。此外，即使内容在窗口内，Self-Attention 对远距离 token 的关注度通常较弱（尽管技术上可以关注任意距离）。这也是为什么生产系统中需要实现对话记忆管理——如滑动窗口（保留最近 N 轮）、摘要压缩（把早期对话总结成简短摘要）、或外部记忆存储（把重要信息存到向量数据库）。

## 五、Temperature 与采样策略

### 5.1 Temperature（温度）

Temperature 控制模型输出的**随机性**，是最常用的调参手段：

```
Temperature = 0    → 模型总是选择概率最高的 token（确定性输出，适合代码、事实查询）
Temperature = 0.5  → 适度随机（平衡准确性和创造性）
Temperature = 1.0  → 标准随机（正常的概率分布）
Temperature > 1.0  → 高度随机（输出可能很离谱，适合创意写作）
```

直觉理解：

```
假设模型要选择下一个词，候选概率分布：
  "是"  → 60%
  "对"  → 25%
  "嗯"  → 15%

Temperature = 0：   永远选 "是"（60% 最高）
Temperature = 0.5：  90% 选 "是"，偶尔选 "对" 或 "嗯"
Temperature = 1.0：  60% 选 "是"，25% 选 "对"，15% 选 "嗯"
Temperature = 2.0：  概率分布变平坦，三个选项概率接近
```

### 5.2 其他采样参数

| 参数 | 作用 | 典型值 |
|------|------|--------|
| **top_p（核采样）** | 只从累计概率达到 p 的候选词中采样 | 0.9 |
| **top_k** | 只从概率最高的 k 个候选词中采样 | 50 |
| **frequency_penalty** | 降低已出现词的再次出现概率（减少重复） | 0~2 |
| **presence_penalty** | 鼓励模型谈论新话题 | 0~2 |
| **stop** | 遇到指定字符串就停止生成 | ["\n\n"] |

**面试常问**：「Temperature 和 Top-P 有什么区别？什么时候用哪个？」

**参考答案**：Temperature 通过缩放概率分布来控制随机性——降低温度使分布更尖锐（更确定），升高温度使分布更平坦（更随机）。Top-P（核采样）则是截断概率分布——只保留累积概率达到 p 的候选词。实际使用中，一般只调其中一个，不同时调。代码生成等需要准确性的场景用低 temperature（0~0.2），创意写作等需要多样性的场景用高 temperature（0.7~1.0）。

## 六、训练过程：大模型是怎么「学会」的

### 6.1 三个阶段

```
阶段 1：预训练（Pre-training）
  ├── 数据：互联网上的海量文本（万亿 token）
  ├── 任务：预测下一个 token（自监督学习）
  ├── 成本：数百万~数亿美元
  └── 结果：一个「什么都知道但不听话」的基座模型

阶段 2：微调（Fine-tuning）
  ├── 数据：人工标注的高质量对话数据（万~百万条）
  ├── 任务：学会「对话格式」和「遵循指令」
  ├── 成本：几千~几万美元
  └── 结果：从「补全文本」变成「回答问题」（ChatGPT 的前身就是 GPT-3 + InstructGPT 微调）

阶段 3：对齐（Alignment / RLHF）
  ├── 数据：人类对模型输出的偏好排序
  ├── 任务：让模型输出更安全、更有帮助、更诚实
  ├── 成本：需要大量人工评估
  └── 结果：ChatGPT 的最终形态——既聪明又听话
```

### 6.2 RLHF：让人类「教」模型

**RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）** 是让 ChatGPT 从「能用」变成「好用」的关键技术：

```
步骤 1：收集人类偏好数据
  给模型同一个问题，让它生成多个回答
  人类标注员排列这些回答的好坏（A > B > C）

步骤 2：训练奖励模型（Reward Model）
  用人类的排序数据训练一个模型，学会「评判回答质量」
  这个模型能给任意回答打分

步骤 3：用强化学习优化 LLM
  让 LLM 生成回答 → 奖励模型打分 → 根据分数调整 LLM 参数
  循环迭代，LLM 越来越会「讨好」人类
```

**2024 年后的新趋势：DPO（Direct Preference Optimization）**

RLHF 需要训练一个额外的奖励模型，流程复杂。DPO 直接用偏好数据优化 LLM，跳过了奖励模型训练步骤，更简单高效。DeepSeek、Llama 3 等新模型都采用了 DPO 或其变体。

### 6.3 面试常问：「预训练和微调有什么区别？」

**参考答案**：预训练是在海量无标注文本上进行自监督学习，让模型学会语言的统计规律和世界知识，成本极高。微调是在预训练模型基础上，用少量高质量标注数据进行有监督学习，让模型学会特定任务的格式和行为（如对话、代码生成）。在实际应用中，我们通常不需要自己预训练或微调，而是通过 Prompt Engineering 来引导已有模型完成特定任务，这就是所谓的「Prompt 即微调」。

## 七、Prompt Engineering：和大模型对话的艺术

### 7.1 基本概念

**Prompt（提示词）** 就是你给大模型的「指令」。Prompt Engineering 是设计高质量提示词的技术——同样的任务，不同的 Prompt 可能导致输出质量天差地别。

### 7.2 核心技巧

#### （1）角色设定（System Prompt）

```
# 差的 Prompt：
写一段关于人工智能的文章

# 好的 Prompt：
你是一位资深的科技记者，擅长用通俗易懂的语言解释复杂技术概念。
请写一段面向普通读者的 AI 科普文章，控制在 500 字以内，
要求：有具体案例、语言生动、避免术语堆砌
```

#### （2）Few-shot Learning（少样本学习）

给模型几个「示例」，让它模仿格式：

```
请将以下句子分类为「正面」或「负面」：

示例 1：这部电影太好看了！→ 正面
示例 2：服务态度很差，不推荐 → 负面
示例 3：物美价廉，下次还来 → 正面

现在请分类：
这家餐厅的菜品味道一般，但环境不错 →
```

#### （3）Chain-of-Thought（CoT，思维链）

让模型「一步步思考」，而不是直接给答案：

```
# 差的 Prompt：
小明有 5 个苹果，给了小红 2 个，又买了 3 个，他现在有几个苹果？

# 好的 Prompt（加了 CoT 提示）：
小明有 5 个苹果，给了小红 2 个，又买了 3 个，他现在有几个苹果？
请一步一步思考。
```

CoT 的魔法在于「请一步一步思考」这几个字。它迫使模型展示推理过程，而不是直接跳到（可能是错误的）答案。研究表明 CoT 能显著提升数学推理和逻辑推理的准确率。

#### （4）结构化输出

```
请以 JSON 格式返回分析结果，包含以下字段：
{
  "sentiment": "正面/负面/中性",
  "confidence": 0.0~1.0,
  "keywords": ["关键词1", "关键词2"],
  "summary": "一句话总结"
}
```

### 7.3 Prompt 的组成部分

```
┌─────────────────────────────────────────────┐
│  System Prompt（系统提示词）                    │
│  ├── 角色定义：「你是一个...」                   │
│  ├── 能力边界：「你可以...，但不要...」          │
│  ├── 输出格式：「请以 JSON/Markdown 格式返回」   │
│  └── 示例：Few-shot examples                   │
├─────────────────────────────────────────────┤
│  Context（上下文/检索结果）                      │
│  ├── RAG 检索到的相关文档                       │
│  ├── 历史对话记录                               │
│  └── 用户提供的参考信息                         │
├─────────────────────────────────────────────┤
│  User Message（用户消息）                       │
│  └── 用户的具体问题或指令                       │
└─────────────────────────────────────────────┘
```

### 7.4 面试常问：「怎么设计一个好的 Prompt？」

**参考答案**：好的 Prompt 需要包含四个要素：明确的角色设定（告诉模型它是谁）、清晰的任务描述（告诉它做什么）、具体的约束条件（格式、长度、语言风格）、以及必要的示例（Few-shot 让模型理解预期输出）。此外，对于复杂推理任务，可以使用 Chain-of-Thought 技术引导模型逐步思考；对于需要特定格式输出的场景，要明确指定 JSON/Markdown 等结构化格式。在生产环境中，还需要对 Prompt 进行 A/B 测试，持续迭代优化。

## 八、Fine-tuning（微调）：教模型新技能

### 8.1 什么是微调？

微调是在**预训练模型**的基础上，用**特定领域的数据**继续训练，让模型学会新任务。

```
预训练模型：什么都知道，但「不听话」
  ↓ 微调（用 1 万条客服对话数据训练）
微调后模型：变成了「专业的客服助手」
```

### 8.2 微调 vs Prompt Engineering：什么时候用哪个？

| 维度 | Prompt Engineering | 微调 |
|------|-------------------|------|
| **成本** | 几乎为零 | 几千~几万美元 |
| **时间** | 几分钟搞定 | 几天~几周 |
| **数据需求** | 不需要训练数据 | 需要标注数据（千~万条） |
| **适用场景** | 80% 的场景 | 需要特定格式/风格/领域的场景 |
| **效果上限** | 受模型能力限制 | 可以突破模型的默认能力 |
| **维护成本** | Prompt 版本管理 | 模型版本管理 + 重新训练 |

**面试结论**：先试 Prompt Engineering，不够用再考虑微调。大部分应用级场景 Prompt 就够了。

### 8.3 LoRA：低成本微调的「银弹」

全量微调需要更新模型的**所有参数**（几百亿个），成本极高。**LoRA（Low-Rank Adaptation，低秩适配）** 是一种高效的微调方法：

```
全量微调：
  更新所有参数（如 70 亿个）
  需要大量 GPU 内存（几百 GB）
  训练时间长

LoRA 微调：
  冻结原始参数，只训练「增量矩阵」（几百 MB）
  GPU 内存需求降低 10 倍以上
  训练速度提升 5-10 倍
  效果接近全量微调的 95%+
```

### 8.4 面试常问：「微调和 RAG 怎么选？」

**参考答案**：RAG 适合需要**实时获取最新信息**的场景（如企业知识库问答），优势是不会产生幻觉、数据可随时更新、不需要重新训练。微调适合需要**改变模型行为模式**的场景（如让模型学会特定的输出格式、语气风格、领域术语），优势是推理时不需要携带大量上下文。两者并不互斥，生产系统中经常同时使用：微调让模型学会领域知识和格式，RAG 提供最新的实时信息。

## 九、Agent：从「聊天」到「干活」

### 9.1 Agent 是什么？

```
普通 LLM 对话：
  用户问 → 模型答（被动回答，只能聊天）

Agent（智能体）：
  用户给目标 → 模型自主规划 → 调用工具 → 观察结果 → 继续决策 → 完成任务
  （主动执行，能操作外部世界）
```

**一句话定义**：Agent = LLM（大脑） + Tools（手脚） + Memory（记忆） + Planning（规划）

### 9.2 Agent 四要素

| 要素 | 作用 | 你的项目对应 |
|------|------|-------------|
| **LLM（大脑）** | 理解意图、推理决策、生成回答 | DeepSeek / MiMo / Qwen |
| **Tools（手脚）** | 与外部世界交互（API调用、文件操作、数据库查询） | Skill 技能系统（HTTP/LLM/FileGen） |
| **Memory（记忆）** | 保持上下文、记住历史对话 | 对话历史 + ChromaDB 知识库 |
| **Planning（规划）** | 拆解任务、制定执行计划 | Agent 四步编排流水线 |

### 9.3 ReAct 模式：Agent 的核心范式

**ReAct（Reasoning + Acting）** 是最主流的 Agent 工作范式，几乎所有 Agent 框架都基于它：

```
用户：「帮我查一下贵州茅台最近一周的股价，并分析走势」

Thought 1（推理）：用户需要股价数据和走势分析。我有关联的「股票行情查询」技能可以获取数据。
Action 1（行动）：调用股票行情查询 API，参数：stockCode=600519, days=7
Observation 1（观察）：API 返回了最近 7 个交易日的开盘价、收盘价、最高价、最低价数据

Thought 2（推理）：拿到了数据，现在需要进行技术分析。
Action 2（行动）：将数据和分析指令发送给 LLM 进行分析
Observation 2（观察）：LLM 返回了技术分析报告

Thought 3（推理）：分析完成，可以给用户最终回答了。
Final Answer：贵州茅台最近一周呈震荡上行趋势...
```

对应你的项目代码：

```
AgentSkillExecutor 中的执行流程就是 ReAct 的实现：

Thought（LLM 思考）：selectSkillsByLLM → LLM 分析用户意图，选择最匹配的技能
Action（执行动作）：skillHandler.execute → 调用技能的 endpoint
Observation（观察结果）：解析 API 返回的 response
→ 如果还需要更多信息，继续循环；否则返回最终答案
```

### 9.4 Function Calling：Agent 的技术基础

**Function Calling（函数调用）** 是让 LLM 能够调用外部工具的技术机制，由 OpenAI 在 2023 年 6 月首先推出：

```
1. 开发者告诉 LLM 有哪些工具可用（通过 JSON Schema 描述）
2. 用户提问
3. LLM 分析后，决定要调用哪个工具，输出结构化的调用指令（JSON）
4. 开发者的代码执行这个调用
5. 把结果返回给 LLM
6. LLM 根据结果生成最终回答
```

**关键理解**：LLM 本身**不能执行任何代码或 API 调用**。它只是「决定」应该调用什么，实际执行是开发者代码完成的。这就是为什么 Agent 系统需要一个「编排层」来协调 LLM 的决策和工具的执行。

对应你的项目：

```
Function Calling 在你项目中的体现：

Skill 的 inputSchema = OpenAI 的 function parameters 定义
AgentSkillExecutor = Function Calling 的执行层
LLM 参数提取 = Function Calling 的参数匹配过程
```

### 9.5 Planning（规划）：让 Agent 会「想」

| 规划策略 | 说明 | 适用场景 |
|---------|------|---------|
| **Plan-and-Execute** | 先生成完整计划，再逐步执行 | 确定性高的任务（如「分析财报」） |
| **Dynamic Planning** | 每步执行后根据结果调整计划 | 不确定性高的任务（如「排查线上 Bug」） |
| **Task Decomposition** | 把复杂任务拆成子任务 | 多步骤任务（如「生成报告」需要数据收集+分析+排版） |

### 9.6 Multi-Agent：多个 Agent 协作

单个 Agent 有局限性——上下文窗口有限、技能有边界。**Multi-Agent** 让多个专长不同的 Agent 协作完成复杂任务：

```
场景：「分析一只股票并生成投资报告」

Router Agent（路由）：分析用户意图，分配任务
  ├── StockAnalyst Agent（股票分析师）：负责获取行情、分析数据
  ├── Researcher Agent（研究员）：负责搜索行业新闻、政策信息
  └── Writer Agent（报告撰写者）：负责整合信息、生成报告

执行流程：
  1. Router 判断需要 3 个 Agent 协作
  2. StockAnalyst 和 Researcher 并行执行（没有依赖）
  3. 两者结果汇总给 Writer
  4. Writer 生成最终报告
```

### 9.7 面试必问：「请介绍你做过的 Agent 项目」

**参考答案模板**（结合你的项目）：

> 我实现了一个企业级 Agent 系统，核心架构是**四步编排流水线**：
>
> **Step 1 - 提示词组装**：Agent 可以关联多个提示词模板，系统通过 LLM 根据用户意图自动选择最相关的模板拼装进系统提示词，而不是全部加载（减少 token 浪费）。
>
> **Step 2 - 知识库检索**：对接了 ChromaDB 向量数据库，实现了完整的 RAG 链路——文档解析→分片→向量化→语义检索。每个知识库独立 Collection，支持 Top-K 检索和关键词降级。
>
> **Step 3 - 技能调用**：采用策略模式设计了可扩展的技能执行框架，支持 HTTP API、LLM 推理、文件生成三种技能类型。LLM 负责从技能池中智能选择和参数提取，Handler 负责实际执行。
>
> **Step 4 - LLM 流式回答**：通过 Spring SSE 实现逐 token 流式输出，前端用 fetch + ReadableStream 实时渲染。每步执行前支持用户取消（AbortController + AtomicBoolean）。
>
> 还实现了**编排模式**——让 LLM 动态决定使用哪个 Agent、按什么顺序执行，支持顺序/并行策略，以及多级降级（LLM 选择失败→默认 Agent→通用 LLM）。

## 十、RAG：让大模型「翻书回答」

### 10.1 为什么需要 RAG？

大模型有两个致命缺陷：

```
缺陷 1：知识有截止日期
  GPT-4 的训练数据截止到 2023 年 12 月
  你问它 2024 年发生的事，它不知道（或胡编）

缺陷 2：没有你的私有数据
  你的企业文档、内部知识库、私有数据库
  大模型训练时从未见过这些数据
```

**RAG（Retrieval-Augmented Generation，检索增强生成）** 的思路：

```
用户提问
  ↓
先从知识库中检索相关文档（像查字典一样）
  ↓
把检索到的内容和用户问题一起发给大模型
  ↓
大模型根据「参考书」来回答（不再是凭空编造）
```

**一句话总结**：RAG = 先查资料，再回答问题。就像开卷考试比闭卷考试准确率高一样。

### 10.2 完整的 RAG 流程

```
                     离线阶段（上传时）                           在线阶段（提问时）
                 ─────────────────                         ─────────────────

  文档上传                                    用户提问:「报销流程是什么？」
      ↓                                              ↓
  文档解析                                    问题向量化: Embed("报销流程是什么？")
  (PDF/Word/TXT → 纯文本)                          ↓
      ↓                                      向量检索: 在 ChromaDB 中找 Top-5
  文档分块                                         ↓
  (按段落/固定长度切分)                         拼接 Prompt:
      ↓                                        system: 你是一个助手...
  向量化                                        context: [检索到的 5 段相关文本]
  (每段文本 → 1536维向量)                       user: 报销流程是什么？
      ↓                                              ↓
  存入向量数据库                                LLM 生成回答（基于检索到的内容）
  (ChromaDB)
```

### 10.3 Chunking（分块）策略

分块是 RAG 中最容易被忽视但影响巨大的环节：

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **固定长度** | 每 500 个字切一块 | 实现简单 | 可能切断段落中间 |
| **按段落/句子** | 按自然段落切分 | 保持语义完整 | 块大小不均匀 |
| **滑动窗口** | 固定长度 + 重叠区域 | 避免边界信息丢失 | 存储量增加 |
| **语义分块** | 用 Embedding 检测语义边界 | 语义最完整 | 计算成本高 |
| **递归分块** | 先按大标题切，再按小标题切，再按段落切 | 层次清晰 | 实现复杂 |

**关键参数**：

```
chunkSize（分块大小）：通常 500~1500 tokens
  太小 → 上下文碎片化，检索到的信息不完整
  太大 → 检索精度下降，可能包含大量无关信息

chunkOverlap（重叠区域）：通常 50~200 tokens
  避免在分块边界处丢失上下文信息
```

### 10.4 Embedding（向量化）：文本变成数字

**Embedding** 是把文本转换成一个**固定长度的数字向量**的过程。语义相近的文本，向量距离也相近：

```
"我想请假" → [0.12, -0.34, 0.56, ..., 0.78]（1536维向量）
"请个假"   → [0.11, -0.33, 0.55, ..., 0.77]（非常接近！）
"今天天气好" → [0.89, 0.45, -0.23, ..., 0.12]（距离很远）
```

**常用 Embedding 模型**：

| 模型 | 提供方 | 维度 | 特点 |
|------|--------|------|------|
| text-embedding-3-small | OpenAI | 1536 | 性价比高 |
| text-embedding-3-large | OpenAI | 3072 | 精度更高 |
| text-embedding-v3 | 阿里云 | 1024~2048 | 中文效果好 |
| BGE-M3 | BAAI | 1024 | 开源，多语言 |

### 10.5 向量数据库

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|---------|
| **ChromaDB** | 嵌入式 | 轻量、Python/Java SDK | 你的项目正在用 |
| **Milvus** | 分布式 | 高性能、支持十亿级向量 | 大规模生产 |
| **Pinecone** | 云服务 | 免运维、开箱即用 | 不想自建 |
| **Weaviate** | 开源 | 支持混合搜索 | 需要关键词+向量结合 |
| **pgvector** | PG 扩展 | 复用现有 PostgreSQL | 已有 PG 基础设施 |

**面试常问**：「向量数据库和传统数据库有什么区别？」

**参考答案**：传统数据库（MySQL）基于精确匹配（WHERE name = '张三'），适合结构化数据的精确查询。向量数据库基于近似最近邻（ANN）搜索，计算向量之间的相似度（余弦相似度/欧氏距离），适合语义级别的模糊检索。比如搜「怎么请假」，传统数据库找不到「请假审批流程」这条记录，但向量数据库能通过语义相似度匹配到它。

### 10.6 检索优化技巧

| 技术 | 说明 |
|------|------|
| **Hybrid Search** | 关键词搜索（BM25）+ 向量搜索，两者结果融合 |
| **Rerank（重排序）** | 粗排（向量检索 Top-50）→ 精排（Reranker 模型从 50 中选 Top-5） |
| **Query 改写** | 用 LLM 把用户问题改写成更适合检索的形式 |
| **Multi-Query** | 把一个问题拆成多个子问题，分别检索后合并 |
| **Metadata 过滤** | 先按元数据（时间、类别）缩小范围，再做向量检索 |

## 十一、流式通信：SSE vs WebSocket

### 11.1 为什么需要流式？

```
非流式（同步）：
  用户等待 5~30 秒 → 看到一大段文字
  体验：焦虑、不确定系统是否卡死

流式（Streaming）：
  用户等待 0.5 秒 → 文字像打字一样逐个蹦出
  体验：流畅、即时反馈、沉浸感强
```

### 11.2 SSE vs WebSocket

| 特性 | SSE（Server-Sent Events） | WebSocket |
|------|--------------------------|-----------|
| **方向** | 服务端 → 客户端（单向） | 双向通信 |
| **协议** | HTTP | 独立协议（ws://） |
| **实现难度** | 简单（标准 HTTP） | 复杂（需要握手、心跳） |
| **Nginx 兼容** | 需要特殊配置（X-Accel-Buffering: no） | 需要升级协议配置 |
| **适用场景** | LLM 流式输出（你只需要服务端推送） | 实时聊天、协同编辑 |

**LLM 场景为什么选 SSE？** 因为 LLM 流式输出天然是「服务端单向推送」——模型一个 token 一个 token 往外蹦，客户端只需要接收和渲染，不需要实时回传。SSE 完美匹配这个需求，且基于标准 HTTP，实现和部署都更简单。

### 11.3 面试常问：「你们项目流式响应怎么实现的？」

**参考答案**：

> 后端使用 Spring 的 SseEmitter 作为 SSE 发射器，通过 LlmSseHelper 封装通用的 LLM 流式调用。LLM API 返回的 SSE 流经过逐行解析后，通过 emitter.send() 推送给前端。
>
> 前端基于 fetch API + ReadableStream 实现 SSE 读取，使用行缓冲处理不完整数据（SSE 数据可能跨多个 TCP 包到达）。读取到的文本片段通过 reactive 变量实时更新到 UI。
>
> 我们还实现了取消机制：前端用 AbortController 中断 fetch 请求，后端用 AtomicBoolean 标记取消状态，每步执行前检查取消标志，确保用户可以随时终止对话。

## 十二、模型幻觉与缓解策略

### 12.1 什么是幻觉（Hallucination）？

模型**自信满满地胡说八道**——输出看起来很合理、语法流畅，但事实是错的。

```
用户：请介绍张三的学术论文《量子计算的未来》
模型：张三教授是清华大学计算机系的教授，他的论文《量子计算的未来》
     发表在 2023 年的 Nature 上，提出了...

实际情况：张三没发过这篇论文，论文名是编的，发表信息也是编的
```

### 12.2 幻觉产生的原因

```
1. 训练数据有噪声：互联网文本中本身就包含错误信息
2. 概率预测的本质：模型在「猜下一个最可能的词」，不是在「查事实」
3. 知识截断：模型不知道自己不知道什么，会「编」出看似合理的内容
4. 过度泛化：把 A 场景学到的知识错误地套用到 B 场景
```

### 12.3 缓解幻觉的策略

| 策略 | 原理 | 你的项目对应 |
|------|------|-------------|
| **RAG** | 用真实数据增强回答，减少「编造」 | 知识库检索→拼接进 Prompt |
| **温度调低** | Temperature=0 让输出更确定，减少随机编造 | 代码中 temperature=0 |
| **引用来源** | 要求模型标注信息来源，便于验证 | — |
| **后验证** | 用另一个 LLM 检查输出的事实性 | — |
| **Grounding** | 限制模型只基于提供的信息回答 | System Prompt 中约束 |

**面试参考答案**：幻觉的根源在于 LLM 是概率预测模型，不是知识库查询。缓解策略主要包括：RAG（用检索到的真实数据作为参考）、Prompt 约束（明确告诉模型「如果不确定就说不知道」）、Temperature 调低（降低随机性）、以及后验证（用规则或另一个模型检查输出的事实性）。其中 RAG 是目前工业界最主流的方案，也是我们项目采用的核心策略。

### 13.2 闭源 vs 开源

```
闭源模型（GPT、Claude、Qwen商业版）：
  优点：效果好、免运维、持续更新
  缺点：数据发送到第三方、有审查限制、成本持续
  适合：大多数商业应用

开源模型（Llama、DeepSeek、Qwen开源版）：
  优点：数据可控、可定制、无审查、长期成本低
  缺点：需要自己部署、效果可能略逊
  适合：数据敏感场景、需要定制化、成本敏感
```

### 13.3 MoE（混合专家）架构

DeepSeek-V3 和 GPT-4 据传都采用了 **MoE（Mixture of Experts）** 架构：

```
传统 Dense 模型：
  所有参数参与每次计算 → 70B 参数 = 70B 计算量

MoE 模型：
  671B 总参数，但每次只激活其中的 ~37B → 计算量和 37B 模型差不多
  但拥有 671B 模型的知识容量

类比：一个公司有 100 个专家，每次决策只叫 5 个最相关的来开会
  → 效率高（不用 100 人都来），但知识库是 100 个人的总和
```

## 十四、面试高频题速查（15 题）

### Q1：什么是大模型？和传统 NLP 有什么区别？
**答**：大模型是参数量达到百亿以上的通用语言模型，通过海量数据预训练获得通用的语言理解和生成能力。传统 NLP 为特定任务训练单一模型，大模型通过 Prompt 切换任务无需重新训练。关键差异在于「涌现能力」——参数规模突破临界点后，模型突然能做以前做不到的事（推理、代码生成等）。

### Q2：解释一下 Transformer 的 Self-Attention？
**答**：Self-Attention 让每个词能「关注」句子中的所有其他词，通过 Q（查询）和 K（键）计算相似度得到注意力权重，再对 V（值）做加权求和。这使得模型能捕捉长距离依赖关系，且支持并行计算（比 RNN 快得多）。

### Q3：Token 是什么？为什么按 Token 计费？
**答**：Token 是模型处理文本的最小单位，由 BPE 分词器将文本切分而成。常见词可能是一个 token，罕见词被拆成多个子词。因为模型的实际计算量与 token 数成正比（不是字数），所以按 token 计费更准确反映成本。

### Q4：Temperature 参数怎么用？
**答**：Temperature 控制输出随机性。0 代表确定性最高（适合代码、事实查询），1 是标准随机，大于 1 是高随机（适合创意写作）。原理是缩放概率分布——温度低使分布更尖锐（集中在最高概率），温度高使分布更平坦。

### Q5：什么是 Prompt Engineering？有什么技巧？
**答**：设计高质量提示词的技术。核心技巧包括：角色设定（System Prompt 定义行为边界）、Few-shot Learning（给示例让模型模仿）、Chain-of-Thought（引导模型逐步思考）、结构化输出（明确指定 JSON 等格式）。

### Q6：什么是 Agent？和普通 LLM 对话有什么区别？
**答**：Agent = LLM + Tools + Memory + Planning。普通 LLM 只能被动回答问题，Agent 能自主规划、调用外部工具、观察结果、继续决策，形成 Reasoning-Acting 的闭环。核心范式是 ReAct（推理+行动交替进行）。

### Q7：解释一下 Function Calling 的工作原理？
**答**：开发者通过 JSON Schema 描述可用工具，LLM 分析用户意图后输出结构化的调用指令（函数名+参数），开发者代码执行调用并将结果返回给 LLM。关键点：LLM 本身不能执行任何操作，只是「决定」该调用什么。

### Q8：什么是 RAG？为什么需要它？
**答**：RAG（检索增强生成）= 先检索再回答。解决大模型知识截止和缺乏私有数据两个问题。流程：文档解析→分块→向量化→存入向量数据库；提问时向量化问题→向量检索 Top-K→拼接到 Prompt 中→LLM 基于检索结果回答。

### Q9：向量数据库和 MySQL 有什么区别？
**答**：MySQL 基于精确匹配（WHERE name = '张三'），向量数据库基于近似最近邻搜索（找语义最相似的内容）。比如搜「怎么请假」，MySQL 找不到「请假审批流程」，但向量数据库能通过语义匹配找到。

### Q10：什么是 Embedding？怎么选择 Embedding 模型？
**答**：Embedding 是把文本转成固定长度数字向量的过程，语义相近的文本向量距离近。选择考虑因素：中文效果（阿里云 text-embedding-v3 比 OpenAI 的中文更好）、维度（越高精度越好但检索越慢）、价格。

### Q11：什么是微调？和 Prompt Engineering 怎么选？
**答**：微调是用特定数据继续训练模型，改变其行为模式。选择原则：先试 Prompt Engineering（成本几乎为零），不够用再考虑微调。Prompt 适合 80% 场景，微调适合需要特定格式/风格/领域知识的场景。LoRA 可以低成本微调。

### Q12：什么是模型幻觉？怎么缓解？
**答**：幻觉是模型自信地输出错误信息。原因：LLM 本质是概率预测，不是知识查询。缓解：RAG（用真实数据增强）、温度调低、Prompt 约束（让模型说「不确定」）、后验证。

### Q13：SSE 和 WebSocket 的区别？LLM 场景为什么选 SSE？
**答**：SSE 是服务端单向推送（基于 HTTP），WebSocket 是双向通信（独立协议）。LLM 流式输出天然是服务端单向推送，SSE 实现更简单、HTTP 兼容性好。Nginx 环境需配置 X-Accel-Buffering: no 防止缓冲。

### Q14：如何设计一个生产级的 Agent 系统？
**答**：需要考虑：编排引擎（支持顺序/并行/动态规划）、工具调用框架（策略模式可扩展）、记忆管理（短期+长期）、RAG 知识库（向量检索+降级）、流式输出（SSE）、可观测性（链路追踪、Token 统计）、降级策略（每个环节都要有 fallback）。

### Q15：你在项目中遇到过什么 AI 相关的坑？怎么解决的？
**答**（结合你的项目）：
1. 云端 PDF 乱码 → 排查发现 RestTemplate Content-Type 缺少 charset=utf-8 + 云端缺少中文字体
2. SSE 在 Nginx 下被缓冲 → 添加 X-Accel-Buffering: no 响应头
3. 向量数据库 405 错误 → LangChain4j API 升级导致不兼容，适配新版 API
4. LLM 选择技能不准 → 在 Prompt 中增加更详细的技能描述和选择规则
